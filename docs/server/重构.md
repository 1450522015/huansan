# 后端重构（`server/`）— 第一层：技术选型与运行约束

本文档记录 **`server/` 新后端** 在 `.ai/core.md` 推进层级中 **第一层已批准内容**，作为后续架构与实现的基线。

---

## 1. 背景与目标

- 现有 `nodejs/` 功能大致可用，但逻辑耦合、难以靠补丁修复，决定在项目根目录新建 **`server/`** 重做后端。
- 目标：**高可靠性、高扩展性（代码与协议层面）**；**不追求尽快上线**。
- 推进节奏遵循 `.ai/core.md`：**每层设计方案 → 技术总监批准 → 再进入下一层**。

---

## 2. 技术栈（方案 B — 定稿）

| 层级 | 选型 | 说明 |
|------|------|------|
| 语言 | **TypeScript（建议 `strict`）** | 契约前置到编译期，降低战斗与状态类逻辑漂移 |
| HTTP | **Fastify** | 插件化注册、与分层边界契合；配合官方/社区插件（如 cors、rate-limit） |
| 校验 | **Zod**（或等价方案） | HTTP 与 Socket 入参统一校验，失败路径一致 |
| 数据库 | **better-sqlite3**，**WAL** | 文件型库，与实践一致 |
| 日志 | **pino**（Fastify 默认生态） | 结构化日志，支撑正常运行期排障 |
| 实时传输 | **Socket.io v4（B1）** | 保留传输层；**消息契约重做**（见下文） |

---

## 3. 实时层（B1）原则

- **传输**：Socket.io。
- **契约**：采用更可靠方案，例如：少量通道 + 载荷内 `type` / **schema 版本** / **correlationId** / **serverTime**；战局维度使用 **`battle:{id}` 等 room**；关键指令支持 **幂等键与明确 ack**；重连后 **显式同步战局快照**（由后端定义，**前端可适配后端**）。
- **与旧客户端事件名不必兼容**：以后端正确性与可演进性为先。

---

## 4. 数据与 Schema 策略（强约束）

- **不做旧库数据迁移**：新系统就绪后，**可接受原数据库内容全部遗弃**。
- **表结构变更**：一律 **只改 DDL**；策略为 **删表重建、遗弃旧数据**，不在「演进式迁移、兼容旧列」上投入。
- **权威数据**：以 SQLite 为准；进程内缓存仅辅助。

---

## 5. 运行与可靠性侧重点

- **单实例、单体部署**；**不推荐 Redis** 等外部中间件。
- **缓存**：**进程内**缓存（如 LRU / 轻量缓存库或受控自研结构），**必须可丢**；重启或异常时 **运行时内存数据不好处理则直接遗弃**，不把工程重心放在「重启恢复运行时态」。
- **进程异常 / 重启**：不作为设计重点；重点放在 **项目正常运行期间** 的行为正确性（校验、事务、协议一致、日志可追溯等）。
- **「重启不重」**（术语）：指 **进程重启 / 崩溃后的状态恢复不作为工程优先级**；运行时内存态难处理则 **丢弃**。与「重启是否重要」：**重启场景不重要**；**正常运行期间** 的可靠性才是重点（详见 §11.1）。

---

## 6. 非目标（当前阶段明确不做）

- 多实例水平扩展、会话粘滞、Socket 集群适配器（如 Redis adapter）。
- 旧数据迁移、渐进式 schema 迁移工具链。
- 为重启/崩溃做的复杂运行时状态恢复（与第 5 节一致）。

## 8. 第二层：架构设计（已定稿）

### 8.1 整体分层（层名 + 职责）

采用 **整洁架构变体**：外层适配器依赖内层，**依赖方向始终向内**。

| 层名 | 职责 |
|------|------|
| **Delivery — HTTP** | Fastify 实例、限流、CORS、错误映射；**按域拆分路由插件**。仅解析上下文与入参、调用 Application、映射 HTTP 响应。 |
| **Delivery — Realtime** | Socket.io 挂载、连接鉴权、**统一入/出站信封**（Zod）、room 管理；不写业务规则，只调 Application。 |
| **Application（用例层）** | 编排：鉴权、加载聚合、调用 **`src/common`**（纯计算）、调用持久化 **端口**、调用实时 **端口**。事务边界在此层或与 Infrastructure 明确协作。 |
| **Ports（接口）** | 由 Application 定义：`UserRepository`、`BattleRepository`、`PresenceStore`、`BattleRealtimeNotifier`、`ProcessCache`、`Clock` 等；Domain 与 **`src/common`** **不** 依赖其实现。 |
| **Infrastructure** | SQLite 实现、进程内缓存实现、**删表重建式 DDL** 入口、日志。实现 Ports。 |
| **Bootstrap** | 读环境变量、组装 Fastify、挂载 Socket、**依赖注入组合根**。 |

**跨层规则**：HTTP 与 Realtime 不得互相依赖具体实现类；二者只依赖 Application。**`src/common`** 与纯领域规则 **不** 引用 Fastify / Socket.io / `better-sqlite3`。

### 8.2 模块划分（模块名 + 单一职责）

| 模块 | 单一职责 |
|------|-----------|
| **auth** | 注册、登录、JWT 签发与校验上下文。 |
| **user** | 用户资料与 **配置 JSON** 的读写入口。 |
| **config** | 服务端侧全局/默认配置（若有）。 |
| **attrs** | **编排**「展示用属性」：从 user 读配置/快照，调用 **`src/common`** 中属性相关 API，返回给 HTTP。自身不复制公式。 |
| **hall / presence** | 在线列表、用户↔socket 绑定（**单进程内存**）；不负责战斗结算。 |
| **pk** | 邀请、取消、应约等 **战前** 流程；进入「战局中」后交给 **battle**。 |
| **battle** | 战局生命周期：开始回合、提交行动、逃跑、战内聊天（若保留）；协调 **`src/common`**（战斗推演）与持久化、并调 `BattleRealtimeNotifier`。 |
| **admin** | 管理端 API；经 Application 用例访问数据，路由不直写 SQL。 |
| **ai**（可选） | AI 出招生成；输入输出为结构化数据，依赖 **`src/common`** 或 battle 只读端口，不反向耦合 HTTP。 |
| **infrastructure-sqlite** | 连接、WAL、busy、**DDL 删表重建**、仓储实现。 |
| **infrastructure-cache** | 进程内 LRU/TTL；可丢；不当作权威来源。 |
| **`server/src/common/`（后端共享纯计算）** | 见 §9；**后端**无状态计算（无状态、入参→出参）；**单体 `server` 内一个目录**；前端仍用根 `common/`。 |

### 8.3 依赖关系（文字图）

```
[HTTP]  ──┐
          ├──► [Application: auth, user, config, attrs, hall, pk, battle, admin, ai]
[Realtime]┘              │
                           │ 调用纯函数 / 数据结构
                           ▼
              [server/src/common — 共享纯计算]
                           ▲
                           │（可选：极小纯规则若不放 common 则放 domain，
                           │  默认优先收敛进 `src/common` 以便逐行核对）
[SQLite / Cache 实现] ——实现——► [Ports]
```

- **Application → `src/common`**：仅通过 **显式导出的函数或小型 façade**；禁止 Application 内散落复制公式。
- **`src/common`**：零 IO；**仅后端**打包引用。**前端**仍用仓库根 **`common/`**（`@common` → `../common`），与 `server` 解耦；双源期间注意对齐，见 `docs/server/代码结构.md`。

## 9. 第二层补充（目录与共享纯计算 `src/common`）

### 9.1 取消根目录 `common/` 承载后端逻辑的设定

- **原状**：部分逻辑放在仓库根下 `common/`，由后端与前端共同引用。
- **新状**：**后端相关实现一律放在 `server/` 下**；**不再**以根目录 `common/` 作为后端或共享运算的归属地（旧目录可在迁移完成后删除或仅保留非代码资源，以你后续指令为准）。

### 9.2 前端通过相对路径引用

- 前端（如 `mobile/`）继续 **`import { … } from '@common/xxx.js'`**，别名指向 **仓库根 `common/`**（**不**指向 `server`）。**禁止**前端 import `server` 内路由、DB、Socket 等。
- **禁止**前端引用：`server` 内 Fastify 路由、Socket 适配器、仓储、环境变量、数据库等 **非纯计算** 代码。

### 9.3 后端共享纯计算目录 `server/src/common/`（业务重中之重）

- **定位**：**后端**侧无状态计算（属性、战况文本、目录数据等；战斗推演逐步迁入）；**与仓库根 `common/` 可并存**，重构以 `server` 为焦点时以本目录为准逐步收敛。
- **性质**：**纯函数为主**；无网络、无磁盘、无全局可变单例（测试与逐行核对友好）。
- **形态**：**与 `server` 同一 `package.json`**；**前端不引用本路径**，仍用根 `common/`。
- **核对**：后续你将 **逐行核对** 本目录；其它层以 **调用此处导出函数** 为主，避免重复实现计算。

### 10.5 Delivery 契约

#### 10.5.1 HTTP

- **通信**：JSON，`Content-Type: application/json`。
- **鉴权**：`Authorization: Bearer <jwt>`（与现网一致或可演进，定稿后写入本节）。
- **路由表**：在第四层按资源列出路径与方法；第三层仅约定 **路由处理器 → 对应 UseCases 方法** 的映射关系由 Bootstrap 注册。

#### 10.5.2 Realtime（Socket.io + 统一信封）

**客户端 → 服务端（示例命名，可调整）**

```ts
type ClientEnvelope =
  | { v: 1; type: 'pk.challenge'; correlationId: string; payload: { targetUsername: string } }
  | { v: 1; type: 'pk.cancel'; correlationId: string; payload: { targetUsername: string } }
  | { v: 1; type: 'battle.submitActions'; correlationId: string; payload: { battleId: BattleId; clientActionId: string; actions: unknown } }
  | { v: 1; type: 'battle.startRound'; correlationId: string; payload: Record<string, never> }
  | { v: 1; type: 'battle.sync'; correlationId: string; payload: { battleId?: BattleId } }
  // …
```

**服务端 → 客户端推送**

```ts
type ServerPushEnvelope =
  | { v: 1; type: 'hall.onlineChanged'; serverTime: IsoDateTimeString; payload: { list: ReadonlyArray<{ userId: UserId; username: string }> } }
  | { v: 1; type: 'battle.roundStarted'; serverTime: IsoDateTimeString; payload: unknown }
  | { v: 1; type: 'battle.roundDone'; serverTime: IsoDateTimeString; payload: { battleId: BattleId; roundNum: number } }
  | { v: 1; type: 'pk.request'; serverTime: IsoDateTimeString; payload: unknown }
  // …
```

**通道（已定稿）**：采用 **双事件名 + 信封**：
- 客户端 → 服务端：仅使用事件 **`message`**，载荷为 **`ClientEnvelope`**（含 `v`、`type`、`correlationId`、`payload`）。
- 服务端 → 客户端推送：仅使用事件 **`push`**，载荷为 **`ServerPushEnvelope`**（含 `v`、`type`、`serverTime`、`payload`）。
- **不再**为每种业务各注册一套顶层 Socket 事件名（避免事件平面失控、便于版本演进与日志统一）。

**Ack**：客户端 `emit('message', envelope, (ack) => …)` 使用 Socket.io **回调式 ack**；`ack` 载荷为 `Result<unknown, AppError>`，且 **携带与请求相同的 `correlationId`**（或由客户端用闭包关联）。**业务结果变更**另通过 `push` 送达双方（如回合开始、回合结束），与单次请求的 ack 分离。

**Room**：连接成功后 `socket.join('battle:' + battleId)`，由 `BattleUseCases` 在状态变更时通过 `BattleRealtimeNotifier` 广播。

### 10.6 模块间通信方式小结

| 关系 | 方式 |
|------|------|
| HTTP → Application | Fastify handler 调 `*UseCases`，无全局单例裸调。 |
| Realtime → Application | 解析 `ClientEnvelope` → 调 `*UseCases` → `ack`；需要广播时经 `BattleRealtimeNotifier`。 |
| Application → `src/common` | 直接函数调用（同进程）。 |
| Application → 数据 | 仅经 **Ports** 接口。 |
| 前端 → 根 `common/` | `import … from '@common/模块.js'`（Vite → 仓库根 `common/`）。 |
| `src/common` → 其它层 | **禁止**（后端 common 不反向依赖 Delivery / Infrastructure）。 |

---

## 11. 术语确认、Socket 定稿与 TypeScript 利弊

### 11.1 「重启不重」

- **含义**：**不是**「重复」的「重」，而是 **「重启场景不作为建设重点」**——与你在第一层中的表述一致：**重启不重要**，重要的是 **后端在持续正常运行期间** 的 **高可靠性**（输入校验、事务与并发边界、信封与幂等、日志与可观测性等）。
- **工程推论**：不为战局运行时内存做复杂的重启恢复；数据库侧亦 **不设**「战局中快照必持久化」类必选需求，除非日后产品明确要求。

### 11.2 Socket 通道（架构师选定）

- 已写入 **§10.5.2**：**`message` + `push` + 回调 ack**，载荷均为 **版本化信封**。

### 11.3 TypeScript 与 JavaScript 的综合利弊（为何第一层仍选 TS）

| 维度 | TypeScript | JavaScript |
|------|--------------|------------|
| **「灵活性」** | 类型报错会在 **改接口/改字段** 时挡住一些「快改」；可用 `unknown` + 窄化、或在边界用 Zod **刻意**保留灵活区。 | 无编译期拦错，改数据结构不易被 **全局** 感知，短期改起来快。 |
| **可读性与协作** | 签名即文档；跨模块（尤其 **`src/common`**）契约清晰，适合 **逐行核对** 与多人长期维护。 | 依赖约定与注释，人一多易出现「同名不同义、字段漂移」。 |
| **可靠性（正常运行期）** | **编译期 + Zod 运行时** 双轨，减少「线上才发现 undefined」类问题；重构`src/common`时 **引用点可机械检查**。 | 主要靠测试与运行时发现，对数值/战斗类逻辑 **回归成本更高**。 |
| **工程成本** | 构建链（`tsc` / `tsx`）、类型维护；**泛型过度**会降低可读性（可用 lint 约束）。 | 工具链简单；大型后类型债会反过来拖慢迭代。 |
| **与前端共用`src/common`** | TS `src/common`可 **导出类型** 给前端 IDE；前端若仍为 JS/Vue，也可只消费 **编译产物** 或保持同包 TS 源码由工具链处理。 | 共用天然无构建差异，但 **契约** 仍建议用 JSDoc 或 Zod 补，否则前后端易分歧。 |

**综合结论（与本项目目标对齐）**：你强调 **正常运行期高可靠**、**`src/common`逐行核对**、**协议可演进**——**TypeScript 的收益大于成本**。「灵活性下降」主要体现在 **改类型时的摩擦**，这是 **用明确契约换正确性** 的有意交换；灵活区应放在 **JSON 边界 + Zod 解析** 与 **少数 well-scoped 的 unknown**，而不是整库长期无类型。

## 12. 第四层：核心功能设计（步骤级，非代码）

> 本节描述 **主路径流程** 与 **按需设计模式**；不写具体代码。批准第四层后，第五层才可按模块 **逐文件实现**。

### 12.1 认证：注册 / 登录（HTTP）

1. 客户端提交用户名、密码（HTTPS 由部署保证）。
2. **Delivery** 校验 JSON 形态 → **AuthUseCases.register / login**。
3. **Application** 检查用户名唯一性、密码哈希策略 → 调用 **UserRepository** 写入或读取。
4. 成功则签发 JWT（含 `uid`、`token_version` 等声明）；失败则返回统一 **AppError**。
5. **Delivery** 映射 HTTP 状态码与响应体（不含敏感内部栈）。

**模式**：**Adapter（触发原因：对接 HTTP 这一外部形状）** — 将 Fastify 请求/响应适配为用例的 DTO 与 `Result`。

---

### 12.2 长连接：连接建立与身份绑定（Realtime）

1. 客户端建立 Socket.io 连接，握手携带 **JWT**（与第三层一致）。
2. **Delivery（Realtime）** 校验令牌 → **AuthUseCases.verifyToken**（或等效端口）。
3. 成功则 **PresenceStore.bind(userId, socketId, username)**；失败则拒绝连接。
4. 向该连接 **push** 一条 **`hall.onlineChanged` 或等价欢迎/就绪事件`**（具体 payload 以实现为准）；并向其它连接广播在线列表变更。
5. **可选步骤**：查询是否存在待处理 PK，若有则 **push** `pk.pending` 类通知（类型名在 `ServerPushEnvelope` 枚举中定稿）。

**模式**：**Adapter（触发原因：Socket.io 连接模型相对应用层为外部系统）**。

---

### 12.3 PK：发起挑战（`message` → `pk.challenge`）

1. 客户端 `emit('message', ClientEnvelope)`。
2. **Delivery** 用 Zod 解析信封 → 路由到 **PkUseCases.challenge**。
3. **Application** 校验：不能挑战自己、双方无其它进行中对局、目标用户存在等。
4. 创建 **等待中** 战局记录（**BattleRepository.createPending**）。
5. 若目标 **在线**：向其 **push** `pk.request`（载荷含发起方展示信息）；向发起方 **ack** 成功（含 `battleId`）。
6. 若目标 **离线**：**ack** 业务失败或「已发送但未送达」策略（产品定一种，写入实现注释）。

**模式**：一般不强行套 State；战局状态仍由 **BattleRepository** 字段表达。若 PK 与战局状态分支极多，可在 **Application 内** 使用 **State（触发原因：明确状态转换表，减少漏分支）** — 视实现复杂度 **按需** 引入。

---

### 12.4 PK：取消 / 应答

**取消**

1. `message` → `pk.cancel` → **PkUseCases.cancel**。
2. 若存在 **等待中** 且参与方匹配 → **BattleRepository.delete**；向对方 **push** `pk.cancelled`（命名以枚举为准）。
3. **ack** 结果。

**应答（同意 / 拒绝）**

1. `message` → `pk.respond` → **PkUseCases.respond**。
2. 加载战局；若非等待中或用户不匹配 → **ack** 错误。
3. **拒绝**：删战局；向发起方 **push** 结果。
4. **同意**：将战局置 **战局中**，写入 **双方配置快照**（字符串化 JSON 存 DB）；双方 **socket.join(`battle:${id}`)**（在 UseCase 成功后由 **BattleRealtimeNotifier** 或专门协调器执行）；向双方 **push**「进入战局」事件；**ack** 成功。

**模式**：**Facade（触发原因：一条消息触发「DB + room + 多路 push」多步协作）** — 在 **PkUseCases** 或窄 **BattleSessionCoordinator** 内聚，避免 Delivery 堆过程代码。

---

### 12.5 战斗：开始回合（`battle.startRound`）

1. `message` 经解析 → **BattleUseCases.startRound(actorUsername)**。
2. 校验：用户在 **战局中**、回合阶段合法、幂等（若同 correlation 重放则 **ack** `duplicate`）。
3. 从 DB 取双方 **配置快照** + 当前回合游标 → 调用 **`src/common`** 生成 **本回合可行动 UI 所需 payload**（或完整 `BattleState` 视图模型）。
4. 通过 **BattleRealtimeNotifier.toBattleRoom** **push** `battle.roundStarted`。
5. **ack** 成功与摘要字段。

**模式**：无额外模式刚需；复杂 UI payload 组装若膨胀，可用 **Facade（触发原因：简化对`src/common`多次调用的组合）** 局限在 **battle 应用服务** 内。

---

### 12.6 战斗：提交行动（`battle.submitActions`）

1. 解析信封 → **BattleUseCases.submitActions**，读取 **`clientActionId`**。
2. **Application** 在 **单事务或明确锁顺序** 内：查战局 → 若已处理过相同 `clientActionId` → **ack** `duplicate: true` 并结束（**幂等**）。
3. 校验双方行动齐备与合法性 → 调 **`src/common` `advanceRound`** 得到下一状态与战报事件列表。
4. 更新 DB（回合数、状态、备注等）；若本回合结束则 **push** `battle.roundDone`；否则 **push** 中间状态（若有）。
5. **ack** 含 **ActionAck**。

**模式**：**State（触发原因：战局具 **等待中 / 战局中 / 已结束** 及回合子阶段，转换规则多）** — 在 **Application** 用显式状态机对象或缩减函数表实现，避免散落 `if`。**Strategy（触发原因：若存在多种结算规则或多模式战斗）** — 仅当产品确认多策略并存时引入。

---

### 12.7 战斗：逃跑、战内聊天（若保留）

**逃跑**

1. `message` → **BattleUseCases.flee** → 校验战局中身份。
2. 调`src/common`或应用层规则决定结算备注 → 更新 DB 为 **已结束**。
3. **push** `battle.fled` 给对方；**ack** 给发起方。

**聊天**

1. `message` → 校验战局与文本长度 → **push** 给对方（可选 **ack** 表示已收到）。

---

### 12.8 战斗：重连同步（`battle.sync`）

1. `message` → **BattleUseCases.getSyncSnapshotForUser**。
2. 以 **用户名 / userId** 查 **战局中** 记录；读取 DB 中持久字段（回合、快照等）组装 **只读视图**。
3. **ack** 返回快照；**不保证** 与重启前内存完全一致（符合「重启不重」）。

---

### 12.9 大厅：在线列表

1. 连接 / 断开时 **HallUseCases** 更新 **PresenceStore** 并 **push** `hall.onlineChanged`。
2. 不在此路径做重计算。

---

### 12.10 管理端（HTTP，占位流程）

1. 管理员鉴权（角色与令牌策略在实现时定稿）。
2. 各路由 → **AdminUseCases** → 仓储；返回列表或变更结果。
3. 涉及「生成 AI 行动」且存在多种算法时，可引入 **Strategy（触发原因：多策略并存）**。

---

### 12.11 设计模式汇总（按需，非堆砌）

| 模式 | 使用位置（建议） | 触发原因 |
|------|------------------|----------|
| **Adapter** | HTTP 插件、Socket `message` 入口 | 对接外部协议形状 |
| **Facade** | `PkUseCases`、或 `BattleSessionCoordinator` | 单入口隐藏多端口协作 |
| **State** | `BattleUseCases` 内对战局/回合子阶段 | 状态转换多、防漏分支 |
| **Strategy** | AI 行动生成、或多种战斗规则并存时 | 多算法可插拔 |
| **Factory / Builder** | 仅当 **BattleState** 或复杂 DTO 构造步骤极多 | 构造复杂度高时再引入 |

**明确不采用**：为「看起来工程化」而加的 **装饰器链、事件总线泛滥** 等，与本项目 **单实例、直白控制流** 目标不符。
