前端就是mobile项目，后端就是nodejs项目

# 前端架构

```
前端，单页应用
除了登录注册和建立长连接，其它通信都用长连接完成

核心模块：
  - shared/socket/socketClient.js  → 长连接客户端（重连、心跳、事件收发）
  - shared/auth/storage.js         → 认证存储（token、用户名、密码）
  - stores/battleStore.js          → 战局状态管理（pk-push、pk-invite-push处理）
  - components/PkDialog.vue        → 全局PK弹框单例
  - app/App.vue                    → 应用入口（全局PK弹框、战局loading遮罩、socket生命周期）
  - pages/HallPage.vue             → 大厅页面（在线用户列表、PK操作）
  - pages/BattlePageV2.vue         → 战局页面（渲染战局、播动画、出招操作）

登录功能
登录成功，后端生成一个唯一token给前端，该用户之前的token变成失效
时间不会让token失效，只有后端重启、重新登录，会让以前的token失效

退出登录，发送login-exit(→后端)

间隔1秒定时检测长连接情况
if 未连接
    根据前端缓存中有没有token判断是否登录
    if 未登录
        关闭长连接
        if 当前不在登录注册页面
            跳转到登录页面
    else
        尝试和后端建立长连接，后端会检查传递的登录token是否失效
        if 过期 或者 其它原因建立失败
            关闭长连接
            跳转到登录页面
        else
            长连接建立成功

间隔5秒定时心跳
if 已建立长连接
    发ping(→后端)

大厅页面
初次进入时，由socket连接自动获取在线用户列表（←后端: online-user-push）
移除在线离线切换按钮
搜索改为前端搜索
空闲用户显示pk按钮，自身无按钮，战局中用户显示不可点击的"战局中"按钮

订阅online-user-push(←后端)
    用最新数据直接替换store中的在线用户列表

pk
发起pk，前端显示目标用户的状态是空闲，就可以点击pk按钮，并发送pk-request{目标用户名}(→后端)
点完pk按钮立即变成不可点击的"已邀请"，3秒后按钮恢复正常
对战中的用户不可发起pk

订阅pk-invite-push{邀请者用户名, 邀请者转数, 邀请者等级, 邀请者职业串, 邀请者坐骑名}(←后端)
    if 当前处于战局loading或战局页面
        忽略
    else
        弹出PK邀请弹框

PK邀请弹框，全局单例，App.vue中渲染
弹框内容：显示邀请者的用户名、转数等级、职业、坐骑等基本信息
底部两个按钮：[接受] [拒绝]
点拒绝 → 发送pk-reject{邀请者用户名}(→后端)，关闭弹框
点同意 → 发送pk-agree{邀请者用户名}(→后端)，进入战局loading
弹框支持手动关闭（点叉号），关闭等效于拒绝但不必发pk-reject
同一时间只显示一个邀请，新邀请到来时覆盖当前弹框

订阅pk-push(←后端)
    if success
        用pk-push中的战局数据更新store
        if 战局描述.状态 == '已结束'
            if 不在战局页面
                弹框提示结果，点确认后退回到大厅
            // 在战局页面时，由战局页面播最后一回合动画后弹框
        else
            if 不在战局页面
                跳转至战局页面
            if 已出招
                进入等待对方出招阶段
            else
                进入出招阶段
    else
        取消战局loading，弹框提示失败原因

战斗
玩家出招后，发送pk-plan{出招数据}(→后端)，进入等待阶段

前端战局阶段，由pk-push中的已出招决定：
- 已出招 = true → 等待对方出招阶段（显示等待提示，不出招按钮）
- 已出招 = false → 出招阶段（显示出招界面）

战局页面渲染规则
从store中读取pk-push中的战局数据，每次收到新数据时的渲染流程：
1. 保存回合信息作为"初始状态"、红黑方作为"结束状态"
2. 如果战局已结束 并且 回合信息不为null
   → 先用初始状态渲染页面（用户看到上一回合开始时的局面）
   → 0.8秒后切换到结束状态渲染（用户看到结算后的局面）
   → 切换完成后弹框提示结果，点确认后退回大厅
3. 其他情况（战局进行中 或 第1回合就结束）
   → 直接用结束状态渲染页面
   → 如果战局已结束（第1回合分出胜负），立即弹框提示结果

关于pk-push中的战局对象
    {
        战局描述: 战局.战局描述,
        红方: 战局.红方,
        黑方: 战局.黑方,
        回合信息: 战局.战局描述.当前回合 === 1 ? null : 战局.回合信息[战局.回合信息.length - 2],
    }
    战局描述中的回合数是最新回合数，第1回合战况结算完时此处是第2回合，也可能是第1回合（战局结算后如果战局结束，不会增加回合数）
    前端根据红黑双方中的用户名，和本地作比对，判断自己是红黑方
    红黑方中的状态是最新值，战况结算之后的
    回合信息中，只有一个元素，代表上一个回合的回合初状态。取length-2是因为engine.js会在结算时push最新回合到数组末尾，所以倒数第二个是待播放的回合（第1回合前没有上一回合，所以是null）
    状态中有个副将列表，是固定的3个元素的数组，对应页面上三个副将位置，为null代表此处无副将，不渲染
    状态中有武将下标，-1代表是主将，其它数字代表该副将在配置和属性中的副将列表中的下标，出招和渲染用的武将下标都是这个
```

# 后端架构

```
后端

核心模块：
  - src/index.js                  → 入口文件（Express、Socket.IO、路由注册）
  - src/services/onlineMap.js     → 在线用户管理（连接、断开、ping、状态）
  - src/services/battleService.js → 战局服务（上下文、PK事件、定时轮询）
  - src/repositories/battleRepo.js → 战局数据库操作
  - src/repositories/userRepo.js   → 用户数据库操作

const 登录用户列表 = []
用户登录后，用户信息存入登录用户列表，登录用户内容（用户名、token、登录时间）

const 在线用户列表 = []
用户建立长连接后，用户信息存入在线用户列表，在线用户内容（用户名、转数、等级、职业串、坐骑名、战斗状态、ping时间）

const 战局上下文列表 = [
    {战局, 红方出招, 黑方出招, 出招计时, 连续断连次数, 人机类型},
]

if 用户在战局上下文列表中能查询到
    if 战局.战局描述.状态 == '已结束'
        发送pk-push{success: true, 战局:engine.js的当前回合数据方法(战局)的返回值, 已出招: false}(→该用户)
    else
        if 该用户是红方
            已出招 = (红方出招 != null)
        else
            已出招 = (黑方出招 != null)
        发送pk-push{success: true, 战局: engine.js的当前回合数据方法(战局)的返回值, 已出招: 已出招}(→该用户)

订阅ping(←前端)
    在线用户列表中对应用户，记录本次ping的时间
    发pong

间隔5秒定时检测长连接情况
轮询在线用户列表
    if 用户上次发ping是10秒前
        移除长连接，移除在线用户列表中对应数据，并向所有长连接广播online-user-push(→所有前端)，内容是在线用户列表

订阅online-user-pull(←前端)
    发送online-user-push(→所有前端)

前端的主页，点保存或者回退
    if 在线用户列表中有对应用户
        广播online-user-push(→所有前端)

订阅login-exit(←前端)
    移除在线用户列表中对应数据，移除对应长连接，并广播online-user-push(→所有前端)
    移除登录用户列表中对应数据

pk
在线用户的战斗状态分为：空闲，战局中

订阅pk-request{目标用户名}(←前端)
    if 发起方空闲 并且 目标方空闲
        给目标方发pk-invite-push{邀请者用户名, 邀请者转数, 邀请者等级, 邀请者职业串, 邀请者坐骑名}(→目标方)
    else
        给发起方发pk-push{success: false, 原因: "对方正在战斗中"}(→发起方)

订阅pk-reject{邀请者用户名}(←前端)
    可选：给邀请者发一条提示（非必要，前端弹框关闭即可）

订阅pk-agree{邀请者用户名}(←前端)
    if 双方都空闲
        双方状态修改为战局中
        根据双方用户名拿到双方配置，邀请者作为红方，调用engine.js的初始化方法生成战局对象，持久化
        创建战局上下文（战局、出招计时=当前时间+9999秒、双方出招对象、连续断连次数=0），存入战局上下文列表
        给双方发送pk-push{success: true, 战局:engine.js的当前回合数据方法的返回值, 已出招: false}(→双方)
    else
        给发起方发送pk-push{success: false, 原因: "对方状态已变更，无法开始战局"}(→发起方)

订阅pk-plan{出招数据}(←前端)
    if 有对应战局
        把玩家出招赋值到战局上下文

间隔1秒轮询战局上下文列表
    if 非人机对战
        if 双方都不在"在线用户列表"
            连续断连次数++
        else
            连续断连次数=0
        if 连续断连次数>=10
            销毁战局上下文，更新战局描述，持久化
            将双方在在线用户列表中的战斗状态改为"空闲"
            广播online-user-push(→所有前端)
        if 双方都已出招 或者 超时
            调用engine.js的结算方法，返回值是战局，覆盖存入战局上下文，清空双方出招，重置出招计时
            给双方发送pk-push，内容为：{success: true, 战局:engine.js的当前回合数据方法的返回值, 已出招: false}(→双方)
            if 战局.战局描述.状态 == '已结束'
                销毁战局上下文，持久化
                将双方在在线用户列表中的战斗状态改为"空闲"
                广播online-user-push(→所有前端)
    if 人机对战
        if 红方不在"在线用户列表"
            连续断连次数++
        else
            连续断连次数=0
        if 连续断连次数>=10
            销毁战局上下文，更新战局描述，持久化
            将红方在在线用户列表中的战斗状态改为"空闲"
            广播online-user-push(→所有前端)
        if 红方已出招并且是人机对战 或者 超时
            调用bot.js的出招方法，返回值是人机的出招，
            然后再调用engine.js的结算方法，返回值是战局，覆盖存入战局上下文，清空双方出招，重置出招计时
            给红方发送pk-push，内容为：{success: true, 战局:engine.js的当前回合数据方法的返回值, 已出招: false}(→红方)
            if 战局.战局描述.状态 == '已结束'
                销毁战局上下文，持久化
                将红方在在线用户列表中的战斗状态改为"空闲"
                广播online-user-push(→所有前端)
```

异常结束场景说明（出招计时=9999秒，意味着只有双方都断线超时才触发异常结束）

超时
- 出招计时到达9999秒前，玩家有充足时间出招，实际不会触发超时
- 9999秒是一个非常大的值，确保除非特殊原因（如双方都断线），否则不会超时

双方断线超10秒
- A和B都从在线列表消失超过10秒 → 战局销毁
- 双方重连后：没有活跃战局 → 进入大厅，无弹框
- 这条仅为兜底清理，确保内存中的战局上下文不会残留

单方断线
- 断线方（假设A）：重连后后端推送pk-push恢复战局，继续游戏
- 在线方（B）：正常等待，不受影响（出招计时没到，断线检测条件不满足）

退出登录
- 退出方：直接回到登录页
- 在线方：对方从在线列表消失，出招计时没到，不触发异常，正常等待对方重连
- 如果退出方不再回来：在线方一直等待，唯一的出口是自己退出或浏览器关掉

所有异常场景最终表现：前端没有复杂的异常UI，该弹框弹框，该等待等待，该清理清理
